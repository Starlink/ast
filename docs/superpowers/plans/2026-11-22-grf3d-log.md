# grf3d_log: a logging 3D graphics module, and Plot3D tests that use it

Status: draft, 2026-11-22, not yet reviewed.

## Why

The Rust port of AST (`starlink-ast-rs`) is porting `Plot3D` (its design: `docs/superpowers/specs/2026-11-22-plot3d-design.md` in that repository).
It checks its 2D `Plot` call for call against `grf_log.c`'s log, but there is no 3D equivalent: `testplot3d.c` draws through PLplot, and the only other `grf3d` modules are PGPLOT, PLplot and the error-reporting stub `grf3d.c`.
This plan adds `src/grf3d_log.c`, a `grf3d` module with no external dependencies that logs every call and can optionally draw an SVG picture through a camera, and a Plot3D test program and fixture-driven tests that use it.
The logs become the oracle the Rust `LogGrf3d` and `Plot3D` must reproduce byte for byte.
The SVG lets a person check C's Plot3D by eye without PLplot, and gives the Rust port's own 3D pictures something to compare against, element by element within pixel rounding (not byte for byte).

## Decided

- **Text is measured as `grf_log.c` measures it, in the text's own plane.**
  The character height, the 0.6 width factor, the descender and the padding are `grf_log.c`'s, applied along the text's baseline and up directions in 3D instead of on the page.
  The Rust scene recorder uses the same model, so its pictures show the layout that was checked against C.
- **The log and the measurement do not depend on a camera.**
  `grf3d.h` has none, and the log must not depend on a viewpoint.
  In particular `astG3DTxExt` does *not* flip the text axes to face an eye, as `grf3d_plplot.c`'s `getTextAxes` does; those flips keep the text's box unchanged anyway, so the SVG applies them only when drawing.
- **Optional SVG through a camera, in the same module**, as `grf_log.c` writes optional SVG beside its log.
  The camera is used only by the SVG; with no SVG file set, nothing reads it.

## The module

### Files and build

- `src/grf3d_log.c` and `src/grf3d_log.h`, modelled on `grf_log.c` and `grf_log.h`, with the same prologue style and a `History` entry (TIMJ).

- Autotools: `libast_grf3d_log.la` beside `libast_grf_log.la` in `Makefile.am` (around lines 686 and 817), and `grf3d_log.h` wherever `grf_log.h` is listed.
- A program needing both links `ast_grf_log-static` and `ast_grf3d_log-static` whole-archive, as `testgrid` does with `ast_grf3d-static` (`ast_tester/CMakeLists.txt:854`).

### Public set-up functions (`grf3d_log.h`)

```c
void astGrf3DLogInit( FILE *logfile );          /* NULL: no logging */
void astGrf3DLogSetScale( double mm_per_world ); /* default 200.0 */
void astGrf3DLogSetSvg( FILE *svgfile, int width, int height ); /* NULL: no SVG */
int  astGrf3DLogSetCamera( float eye[3], float target[3], float up[3], float screen );
int  astGrf3DLogAutoCamera( float lbnd[3], float ubnd[3] );
void astGrf3DLogClose( void );
```

`astGrf3DLogInit` resets every attribute to its default, as `astGrfLogInit` does.

`mm_per_world` is the 3D analogue of `grf_log.c`'s page: physical millimetres per 3D world unit, the same along every axis (`grf3d.h` assumes equally scaled axes).
Its default of 200 matches `grf_log.c`, whose unit square spans 200 mm, so a unit cube gets the same character height as a 2D unit page (0.02 world units).
A Plot3D whose graphics box is, say, 100 pixels on a side sets it so the characters come out a sensible size.

`astGrf3DLogSetSvg` writes the SVG header as `astGrfLogSetSvg` does (same background, default 720 by 540); `astGrf3DLogClose` closes it.
`astGrf3DLogSetCamera` and `astGrf3DLogAutoCamera` port `grf3d_plplot.c`'s `PL3DSetCamera` and `PL3DAutoCamera`: `screen` zero gives an orthographic projection, otherwise a perspective one with the screen at that distance from the eye; the auto camera fits the given 3D box into the SVG page.
Neither is logged, and neither changes the log.

### The eight `grf3d.h` functions

Every number is printed with the same `printf` formats as the matching `grf_log.c` line, and each line starts with the function name without the `ast` prefix (`G3DLine`, `G3DText`, …).

- **`astG3DAttr`**: identical to `astGAttr` in `grf_log.c`: the same five attribute arrays and defaults, the same unknown-attribute error text with `astG3DAttr` in it, the same log line.
  Keep the arrays separate from `grf_log.c`'s, since a program links both.
- **`astG3DCap`**: answers 0 for every capability, as `astGCap` does for everything but `GRF__SCALES`, which has no 3D meaning: no escape sequences, no `M` justification.
- **`astG3DFlush`**: logs `G3DFlush`, returns 1.
- **`astG3DLine`**: logs the point count and every point (`G3DLine n=%d` then the points at `%.3f`).
  `astGLine` logs only the two end points and skips closed lines; this module is new and is the oracle, so it logs everything rather than copying that.
- **`astG3DMark`**: logs the type, the normal vector and every point, for the same reason.
- **`astG3DQch`**: `ch = ChrHtMM() / mm_per_world`, with `ChrHtMM` as in `grf_log.c` (4 mm × the text `Size` attribute, a size of zero or less treated as 1).
  Logs `G3DQch ch=%.6f`.
- **`astG3DText`**: logs the text, reference point, justification, up vector and normal vector.
  It draws nothing.
- **`astG3DTxExt`**: see below.
  Logs the text, reference point, justification, the four corners and `bl`.

With an SVG file set, `astG3DLine`, `astG3DMark` and `astG3DText` also draw, after logging:

- lines and markers by projecting each point through the camera (`grf3d_plplot.c`'s `transform`) and mapping the result to integer pixels as `grf_log.c`'s `SvgX` and `SvgY` do, with `grf_log.c`'s colour table, line widths and marker shapes;
- text as `grf3d_plplot.c` draws it: build the text axes as `astG3DTxExt` does, apply `getTextAxes`' flips for this camera (adjusting the justification as it does), project the reference point and the baseline and up directions, and write an SVG `<text>` at the projected point, rotated to the projected baseline, its font size `grf_log.c`'s 14 pixels scaled by the projected character height.
  Text is not foreshortened, as in the PLplot backend.

Elements are written in call order; no depth sorting.

### `astG3DTxExt` in the text plane

1. **Justification** as in `grf_log.c`: the first character kept if it is `T`, `C` or `B`, otherwise `C` (so `M` becomes `C`); the second kept if it is `L`, `C` or `R`, otherwise `C`; a NULL `just` gives `CC`.
2. **Text axes**, all in `float`:
   - `tz` = `norm`, normalised.
     A zero `norm` means "towards the camera" in `grf3d.h`, and the log has no camera; report `AST__GRFER` ("astG3DTxExt: Zero length normal vector supplied.") unless the test programs show Plot3D passing a zero normal on an ordinary path, in which case raise it before choosing a rule, because the Rust side must copy the rule.
   - `tx` = `up` × `tz`, `ty` = `tz` × `tx`, each normalised, as `getTextAxes` builds them before its camera flips.
     This projects `up` onto the text plane, as `grf3d.h` specifies.
   - A zero-length `tx` (up parallel to the normal) reports `AST__GRFER`, as `grf_log.c` does for a zero up-vector.
3. **Box in text-plane millimetres**: exactly `grf_log.c`'s `phys_hu`, `phys_hd`, `phys_w`, `padded_w`, `cx_mm`, `cy_mm`, `half_w_mm` and `half_h_mm`, with the same expressions and the same `float`/`double` mix.
   There is no `alpha`/`beta` and no sign flip of the up vector: the text plane is isotropic.
4. **Corners in 3D world units**, with `s = 1 / mm_per_world`:
   - centre `c = ref + s*(cx_mm*tx + cy_mm*ty)`;
   - corners anti-clockwise starting at the bottom left, as `grf3d.h` requires: `c - s*hw*tx - s*hh*ty`, `c + s*hw*tx - s*hh*ty`, `c + s*hw*tx + s*hh*ty`, `c - s*hw*tx + s*hh*ty`.
5. **`bl`**, the left-hand end of the baseline: the point at `x = -padded_w/2` and on the baseline (`y = 0` relative to the baseline) in text-plane terms, mapped to 3D the same way.
   Work this out from the box arithmetic in step 3 and write the derivation in a comment.
6. An empty or NULL `text` gives all-zero corners and `bl`, as `astGTxExt` does.

Every arithmetic step stays in the order and precision written above.
The Rust port copies it operation for operation, so any reordering or change of precision here is a change to the oracle.

## Tests

The aim is a Plot3D test suite that covers what `plot3d.c` does, not only the Fortran test's path.

### `ast_tester/testplot3dlog.c`

Modelled on `testgrid.c`: takes a Native or FITS input holding a 3D FrameSet, Plot3D attributes, a graphics box (six numbers, as `astPlot3D` takes), an optional `mm_per_world`, the log file and an action list, then:

- builds the Plot3D with `astPlot3D`;
- runs a checkdump round trip (`astToString` / `astFromString`, then `astEqual`) and writes the Native dump to a second output file, so the Rust side can compare dumps byte for byte;
- performs the actions, logging every `grf3d` call.

Actions, so one program covers the drawing methods:

- `grid`: `astGrid`;
- `border`: `astBorder`;
- `text`: `astText` with a given string, position, 3-element up vector and justification;
- `mark`: `astMark` with given positions and type;
- `outline`: `astRegionOutline`, for a Region input;
- each refused method (`astBoundingBox`, `astClip`, `astCurve`, `astGenCurve`, `astGridLine`, `astPolyCurve`): call it, expect the error, log the error code and message.

### Fixture-driven cases

A `fixtures/plot3d/cases.txt` in the style of `fixtures/plot/cases.txt`, with a reference log per case, compared by a `cmake/run_grid_test.cmake`-style script.
Cases to cover at least:

- `plot3d-test1.ast` with default attributes (the Fortran test's case);
- each value of `RootCorner`;
- a non-default `Norm`, and text and markers drawn with it;
- per-plane attributes (`Grid_XY`, `Colour_YZ`, …) and axis-3 attributes (`Gap(3)`, `Label(3)`, `LabelUp(3)`, …);
- attributes Plot3D ignores (`Edge`, `DrawTitle`, `TitleGap`), set and shown to have no effect;
- explicit `Gap` and `MinTick` on each axis, which drive `SetTickValues` on the inner Plots;
- a FrameSet built from a 3D FITS header (a spectral cube: RA, Dec and frequency);
- a FrameSet whose current Frame has been changed after construction, to exercise Plot3D's `SetCurrent` override;
- `astRemoveFrame` and `astClear(Current)` on a Plot3D, followed by a grid;
- a non-unit graphics box with a matching `mm_per_world`.

The reference logs are generated by the CMake build on the reference platform and committed; `PLAN.md` gets a batch entry for them, as Batch 12 has for `testgrid`.

`testplot3dlog` also takes an optional SVG file, size and camera (eye, target, up, screen; or "auto").
A few cases write SVG at fixed cameras: orthographic and perspective, the default `RootCorner` and one other, and text seen from behind and upside down so the flips show.
Those SVGs are committed for the Rust port to compare against; the C tests themselves only check that the SVG is written and well formed, since the log is the C oracle.

## Out of scope

- Any change to `plot3d.c` or `grf3d.h`.
  If a test exposes a Plot3D bug, fix it separately with a `History` entry, and tell the Rust port so it can follow.
- PNG, PDF or any picture other than SVG.
- Depth sorting or hidden-line removal in the SVG.

### Task 4: testplot3dlog and the first fixture-driven case

Files: `ast_tester/testplot3dlog.c`, `ast_tester/CMakeLists.txt`, `cmake/run_plot3dlog_test.cmake`, `ast_tester/fixtures/plot3d/cases.txt`, `ast_tester/fixtures/plot3d/expected/test1.log`, `ast_tester/fixtures/plot3d/expected/test1.dump`, `ast_tester/fixtures/DIST_MANIFEST`.

Command line of `testplot3dlog`:

```
testplot3dlog --in FILE [--attr STR] --box "x1 y1 z1 x2 y2 z2" --bbox "x1 y1 z1 x2 y2 z2"
              [--mm N] [--log FILE] [--dump FILE] [--svg FILE [W H]]
              [--camera "ex ey ez tx ty tz ux uy uz screen"] --do ACTION [--do ACTION ...]
```

`--in` reads FITS cards through a FitsChan when the file ends in `.head`, otherwise a Native dump through `astFromString`.
`--svg` always calls `astGrf3DLogAutoCamera` on the graphics box first, then `astGrf3DLogSetCamera` if `--camera` is given.
The program builds the Plot3D, runs the checkdump round trip (`astToString`, `astFromString`, `astEqual`, and the re-serialised string equal to the first), writes the first dump to `--dump`, then performs the actions in order.
Actions:

- `grid`, `border`, `outline` (`astRegionOutline` with the input object, which must be a Region), `refused` (each of `astBoundingBox`, `astClip`, `astCurve`, `astGenCurve`, `astGridLine`, `astPolyCurve`; each error's code name and message are written to the log file as `ERR <code> <message>` lines, the status cleared after each);
- `text:STRING:x,y,z:ux,uy,uz:JUST`, `mark:TYPE:x,y,z[;x,y,z...]`;
- `set:ATTRS`, `clear:ATTR`, `setcurrent:N`, `clearcurrent`, `removeframe:N`.

Every action also writes an `ACTION <name>` line to the log so the oracle shows where each call sequence starts.
Any AST error during an action other than `refused` fails the program with the message on stdout.
